主章节

Rust/codex-rs

在 Rust 代码所在的 codex-rs 文件夹中：

  • crate 名称都以 codex- 为前缀。例如，core 文件夹的 crate 名称是 codex-core。
  • 使用 format! 时，如果变量可以直接内联到 {} 中，就应当内联。
  • 如果仓库依赖某些命令，例如 just、rg 或 cargo-insta，而这些命令尚未安装，应先安装它们，再运行这里的指令。
  • 绝对不要新增或修改任何与 CODEX_SANDBOX_NETWORK_DISABLED_ENV_VAR 或 CODEX_SANDBOX_ENV_VAR 相关的代码。
  • 代理运行在沙箱里，每次使用 shell 工具时都会设置 CODEX_SANDBOX_NETWORK_DISABLED=1。任何现有代码若使用 CODEX_SANDBOX_NETWORK_DISABLED_ENV_VAR，作者通常已经考虑了这个事实。它常用于让作者知道在当前沙箱限制下无法运行的测试提前退出。
  • 类似地，当通过 Seatbelt（/usr/bin/sandbox-exec）启动进程时，子进程会设置 CODEX_SANDBOX=seatbelt。若集成测试需要自己运行 Seatbelt，这类测试无法再运行在 Seatbelt 之下，因此检查 CODEX_SANDBOX=seatbelt 并按需提前退出也是合理做法。
  • 始终按照 Clippy 的 collapsible_if 建议折叠可合并的 if 语句。
  • 始终按照 Clippy 的 uninlined_format_args 建议，在可能时内联 format! 参数。
  • 在可能时，使用方法引用替代闭包，遵循 redundant_closure_for_method_calls。
  • 避免布尔值或含糊的 Option 参数，因为它们会迫使调用方写出 foo(false) 或 bar(None) 这类难读调用。优先使用枚举、具名方法、newtype 或其他惯用 Rust API 形状，让调用点自解释。
  • 如果无法调整 API，又必须在 Rust 中写小型的位置字面量调用点，则遵循 argument_comment_lint 约定。
  • 传入 None、布尔值和数字字面量等不透明位置参数时，在参数前添加精确的 /*param_name*/ 注释。
  • 字符串或字符字面量默认不需要此类注释，除非注释确实带来额外清晰度。
  • 注释中的参数名必须与被调用函数签名中的参数名完全一致。
  • 可以运行 just argument-comment-lint 来在本地执行该检查。它由 Bazel 驱动，首次运行可能较慢；Bazel 预热后，增量运行通常应低于 15 秒。多数情况下，更合适的做法是更新 PR，让 CI 负责检查，或者在提交 PR 后异步运行该检查。CI 会检查三个平台，本地运行只覆盖当前平台。
  • 在可能时，让 match 语句保持穷尽性，并避免通配符分支。
  • 新增 trait 应包含文档注释，说明该 trait 的角色，以及实现方应该如何使用它。
  • 不鼓励在 Rust trait 中使用 #[async_trait] 和 #[allow(async_fn_in_trait)]。
  • 优先使用原生 RPITIT trait 方法，并在返回的 future 上显式声明 Send 约束，就像 3c7f013f9735 / #16630 中的做法。
fn foo(&self, ...) -> impl std::future::Future<Output = T> + Send;
  • 实现仍然可以使用 async fn foo(&self, ...) -> T，前提是它满足上述契约。
  • 不要把 #[allow(async_fn_in_trait)] 当成绕过显式 future 契约写法的捷径。
  • 写测试时，优先比较整个对象的相等性，减少逐字段断言。
  • 不要把通用产品文档或面向用户的文档添加到 docs/ 文件夹。官方 Codex 文档存放在其他地方。例外是 app-server API 文档，这一点在下方 app-server 指南中另有说明。
  • 优先使用私有模块，并显式导出 public crate API。
  • 如果修改 ConfigToml 或其嵌套配置类型，运行 just write-config-schema 更新 codex-rs/core/config.schema.json。
  • 处理 MCP 工具调用时，优先使用 codex-rs/codex-mcp/src/mcp_connection_manager.rs 管理工具和工具调用的变更。目标是缩小修改范围，并复用现有抽象，减少把代码穿透多层函数调用的情况。
  • 如果修改 Rust 依赖（Cargo.toml 或 Cargo.lock），从仓库根目录运行 just bazel-lock-update 刷新 MODULE.bazel.lock，并把该锁文件更新纳入同一变更。
  • 依赖变更后，从仓库根目录运行 just bazel-lock-check，这样本地就能提前发现锁文件漂移。
  • Bazel 不会自动把源树文件暴露给编译期 Rust 文件读取。如果新增 include_str!、include_bytes!、sqlx::migrate! 或类似的编译期文件/目录读取，就要更新对应 crate 的 BUILD.bazel（compile_data、build_script_data 或 test data）。否则 Cargo 可能通过，Bazel 仍会失败。
  • 不要创建只被引用一次的小型 helper 方法。
  • 避免大型模块。
  • 优先新增模块承载新功能，减少继续扩张现有模块。
  • Rust 模块目标控制在 500 行以内，测试代码除外。
  • 如果一个文件超过约 800 行，应把新功能放入新模块，除非存在强有力且已记录的理由继续扩展该文件。
  • 该规则尤其适用于已经容易吸收无关变更的高频文件，例如 codex-rs/tui/src/app.rs、codex-rs/tui/src/bottom_pane/chat_composer.rs、codex-rs/tui/src/bottom_pane/footer.rs、codex-rs/tui/src/chatwidget.rs、codex-rs/tui/src/bottom_pane/mod.rs，以及类似的中心编排模块。
  • 从大型模块抽取代码时，把相关测试和模块/类型文档也移向新的实现位置，让不变量靠近负责它们的代码。
  • 除非变更很小，否则避免向 codex-rs/tui/src/chatwidget.rs 新增独立方法；优先使用新模块/文件，让 chatwidget.rs 聚焦编排职责。
  • 运行 Rust 命令（例如 just fix 或 cargo test）时要有耐心，绝对不要用 PID 强杀它们。Rust lock 可能导致执行较慢，这是预期现象。

完成 Rust 代码变更后的固定动作：在 codex-rs 目录运行 just fmt。无需为这个命令向用户请求批准。

  1. 先运行被修改项目的专项测试。例如，如果修改了 codex-rs/tui，运行 cargo test -p codex-tui。
  2. 专项测试通过后，如果修改涉及 common、core 或 protocol，运行完整测试套件：cargo test，或者在已安装 cargo-nextest 时运行 just test。日常本地运行避免使用 --all-features，因为它会扩展构建矩阵，并显著增加 target/ 磁盘占用。只有确实需要完整 feature 覆盖时才使用它。项目级或单项测试可以直接运行；完整测试套件需要先询问用户。

在最终确认较大的 codex-rs 变更之前，应在 codex-rs 目录运行 just fix -p <project>，修复代码中的 linter 问题。优先用 -p 限定项目范围，避免缓慢的全工作区 Clippy 构建；只有修改了共享 crate 时才运行未限定项目的 just fix。运行 fix 或 fmt 后，不要再次运行测试。

边界控制

codex-core crate

随着时间推移，codex-core crate（定义在 codex-rs/core/）已经变得臃肿。它是最大的 crate，因此把新东西加进 codex-core 往往最省事。问题是，这会让新代码依赖 codex-core，或继续扩大 codex-core 的体积。

因此：抵制向 codex-core 添加代码的冲动。

尤其在引入新概念、新功能或新 API 时，在添加到 codex-core 之前，先考虑：

  • 是否存在 codex-core 之外的现有 crate，能更恰当地承载这些新代码。
  • 是否已经到了为新功能引入一个新的 Cargo workspace crate 的时机，并按需重构现有代码。

同样，在代码评审时，如果 PR 会不必要地向 codex-core 添加代码，不要犹豫，应明确推动修正。

TUI

TUI 风格与代码约定

TUI 风格约定

参见 codex-rs/tui/styles.md。

TUI 代码约定

使用 ratatui 的 Stylize trait 提供的简洁样式 helper。

  • 基础 span：使用 "text".into()。
  • 带样式 span：使用 "text".red()、"text".green()、"text".magenta()、"text".dim() 等。
  • 优先使用这些 helper，减少直接构造 Span::styled 和 Style。
  • 示例：patch 摘要中的文件行，期望写法如下。
vec!["  └ ".into(), "M".red(), " ".dim(), "tui/src/app.rs".dim()]

TUI Styling（ratatui）

  • 优先使用 Stylize helper："text".dim()、.bold()、.cyan()、.italic()、.underlined()，减少手写 Style。
  • 优先使用简单转换：span 用 "text".into()，line 用 vec![...].into()。当类型推断含糊时，例如 Paragraph::new 或 Cell::from，使用 Line::from(spans) 或 Span::from(text)。
  • 运行时计算得到的样式可以使用 Span::styled；Span::from(text).set_style(style) 也可以接受。
  • 避免硬编码白色：不要使用 .white()；优先使用默认前景色。
  • 组合样式时，通过链式调用提高可读性，例如 url.cyan().underlined()。
  • 单个元素优先使用 "text".into()；只有在目标类型不明显，或者 .into() 会要求额外类型标注时，才使用 Line::from(text) 或 Span::from(text)。
  • 构造行时，如果目标类型明显且无需额外类型标注，使用 vec![...].into()；否则使用 Line::from(vec![...])。
  • 避免无意义改写：没有明确可读性或功能收益时，不要在等价形式之间来回重构，例如 Span::styled 与 set_style，或 Line::from 与 .into()。遵循文件局部约定，也不要仅为满足 .into() 而引入类型标注。
  • 保持紧凑：优先选择 rustfmt 后仍能保持单行的形式。如果只有 Line::from(vec![...]) 或 vec![...].into() 其中一种能避免换行，就选择它；如果两者都换行，选择换行更少的形式。

文本换行

  • 始终使用 textwrap::wrap 包装纯字符串。
  • 如果有 ratatui Line 需要换行，使用 tui/src/wrapping.rs 中的 helper，例如 word_wrap_lines 或 word_wrap_line。
  • 如果需要缩进换行后的行，并且可以使用 RtOptions 中的 initial_indent / subsequent_indent 选项，就使用这些选项，减少手写逻辑。
  • 如果有一组行需要统一添加前缀，且首行和后续行可选地使用不同前缀，使用 line_utils 中的 prefix_lines helper。

快照测试

这个仓库使用快照测试（通过 insta），尤其在 codex-rs/tui 中，用来验证渲染输出。

要求：任何影响用户可见 UI 的变更，包括新增 UI，都必须包含相应的 insta 快照覆盖。若已有快照覆盖相关行为，则更新现有快照；若没有，则新增快照测试。应在 PR 中审查并接受快照更新，这样 UI 影响便于评审，未来差异也保持可视。

当 UI 或文本输出的变化是有意的，按以下步骤更新快照：

  1. 运行测试生成更新后的快照：cargo test -p codex-tui。
  2. 检查待处理快照：cargo insta pending-snapshots -p codex-tui。
  3. 直接阅读仓库中生成的 *.snap.new 文件，或预览指定文件：cargo insta show -p codex-tui path/to/file.snap.new。
  4. 只有在打算接受该 crate 的全部新快照时，运行 cargo insta accept -p codex-tui。

如果没有安装该工具：

cargo install --locked cargo-insta

测试断言

  • 测试应使用 pretty_assertions::assert_eq，以获得更清晰的差异输出。如果测试模块尚未导入它，就在顶部导入。
  • 尽可能优先做深度相等比较。对整个对象使用 assert_eq!()，减少逐字段断言。
  • 避免在测试中修改进程环境；优先从上层传入环境派生的标志或依赖。

在测试中启动工作区二进制（Cargo 与 Bazel）

  • 当测试需要启动一方仓库内二进制时，优先使用 codex_utils_cargo_bin::cargo_bin("...")，减少使用 assert_cmd::Command::cargo_bin(...) 或 escargot。
  • 在 Bazel 下，二进制和资源可能位于 runfiles 中；使用 codex_utils_cargo_bin::cargo_bin 可以解析出绝对路径，即使发生 chdir 后仍保持稳定。
  • 在 Bazel 下定位 fixture 文件或测试资源时，避免使用 env!("CARGO_MANIFEST_DIR")。优先使用 codex_utils_cargo_bin::find_resource!，让路径在 Cargo 和 Bazel runfiles 下都能正确解析。

核心集成测试

  • 编写端到端 Codex 测试时，优先使用 core_test_support::responses 中的工具。
  • 所有 mount_sse* helper 都会返回 ResponseMock；保留它，以便断言发往 /responses 的 POST 请求体。
  • 当测试只应发出一个 POST 时，使用 ResponseMock::single_request()；需要检查每个捕获到的 ResponsesRequest 时，使用 ResponseMock::requests()。
  • ResponsesRequest 提供 body_json、input、function_call_output、custom_tool_call_output、call_output、header、path、query_param 等 helper，让断言能够面向结构化 payload，而非手工挖 JSON。
  • 使用提供的 ev_* 构造器和 sse(...) 构建 SSE payload。
  • 优先使用 wait_for_event，减少使用 wait_for_event_with_timeout。
  • 优先使用 mount_sse_once，减少使用 mount_sse_once_match 或 mount_sse_sequence。

典型模式如下：

let mock = responses::mount_sse_once(&server, responses::sse(vec![
    responses::ev_response_created("resp-1"),
    responses::ev_function_call(call_id, "shell", &serde_json::to_string(&args)?),
    responses::ev_completed("resp-1"),
])).await;

codex.submit(Op::UserTurn { ... }).await?;

// Assert request body if needed.
let request = mock.single_request();
// assert using request.function_call_output(call_id) or request.json_body() or other helpers.
API

App-server API 开发最佳实践

这些指南适用于 codex-rs 中的 app-server protocol 工作，尤其是：

  • app-server-protocol/src/protocol/common.rs
  • app-server-protocol/src/protocol/v2.rs
  • app-server/README.md

核心规则

  • 所有活跃 API 开发都应发生在 app-server v2 中。不要向 v1 添加新的 API 表面。
  • 遵循 payload 命名一致性：请求 payload 使用 *Params，响应使用 *Response，通知使用 *Notification。
  • RPC 方法暴露为 <resource>/<method>，并保持 <resource> 为单数，例如 thread/read、app/list。
  • 除 tagged union 或显式兼容性要求需要定向 rename 外，线上的字段始终使用 camelCase，并通过 #[serde(rename_all = "camelCase")] 表达。
  • 例外：config RPC payload 应使用 snake_case，以匹配 config.toml key。可参考 app-server-protocol/src/protocol/v2.rs 中的 config read/write/list API。
  • v2 请求、响应、通知类型始终设置 #[ts(export_to = "v2/")]，让生成的 TypeScript 落入正确 namespace。
  • 不要在 v2 API payload 字段上使用 #[serde(skip_serializing_if = "Option::is_none")]。
  • 例外：client-to-server 请求如果刻意没有 params，可以使用：params: #[ts(type = "undefined")] #[serde(skip_serializing_if = "Option::is_none")] Option<()>。
  • 保持 Rust 与 TypeScript 的 wire rename 一致。如果字段或 variant 使用 #[serde(rename = "...")]，就添加匹配的 #[ts(rename = "...")]。
  • 对于可辨识联合类型，在两个序列化器中都使用显式 tag：#[serde(tag = "type", ...)] 和 #[ts(tag = "type", ...)]。
  • API 边界优先使用普通 String ID；如需 UUID 解析或转换，在内部处理。
  • 时间戳应为整数 Unix 秒（i64），命名为 *_at，例如 created_at、updated_at、resets_at。
  • 实验性 API 表面使用 #[experimental("method/or/field")]。需要字段级 gate 时派生 ExperimentalApi；如果只有方法中的部分字段是实验性的，在 common.rs 中使用 inspect_params: true。

Client-to-server 请求 payload（*Params）

  • 每个可选字段都必须标注 #[ts(optional = nullable)]。不要在 client-to-server 请求 payload（*Params）之外使用 #[ts(optional = nullable)]。
  • 可选集合字段，例如 Vec、HashMap，必须使用 Option<...> 加 #[ts(optional = nullable)]。不要用 #[serde(default)] 表达可选集合，也不要在 v2 payload 字段上使用 skip_serializing_if。
  • 如果希望省略布尔字段时含义为 false，使用 #[serde(default, skip_serializing_if = "std::ops::Not::not")] pub field: bool，减少使用 Option<bool>。
  • 新增 list 方法时，默认实现游标分页：请求字段为 pub cursor: Option<String> 和 pub limit: Option<u32>；响应字段为 pub data: Vec<...> 和 pub next_cursor: Option<String>。

开发流程

  • 当 API 行为变化时，更新 app-server 文档/示例，至少更新 app-server/README.md。
  • API shape 变化时，重新生成 schema fixture：just write-app-server-schema。
  • 如果影响实验性 API fixture，也运行 just write-app-server-schema --experimental。
  • 使用 cargo test -p codex-app-server-protocol 验证。
  • 避免编写只断言 common.rs 中单个请求字段实验性标记的样板测试；优先依靠 schema 生成/测试和行为覆盖。
